# Implementation report — 31 interactive screen types

## Starting point

The project was a static reveal.js 3.8 + jQuery presentation template with a minimal SCORM 1.2 wrapper (`js/scormfunctions.js`). That wrapper reported a fixed page score and time-based completion. Questions were hand-coded in `js/questions.js`, and there was no authoring interface.

The reference project ([edumints-scorm-mcp](https://github.com/kemalyy/edumints-scorm-mcp), MIT) is a Python MCP server. Its documented screen schemas were used as the functional specification, but none of its code was copied. Everything was implemented natively in this project's stack:
- static files with plain browser JavaScript and no build step;
- reveal.js remains the slide engine;
- the only new runtime dependency is lottie-web, loaded only by the `lottie` type.

### Studio features

- **Screens**: add (inserted after the current screen), duplicate, delete, and reorder by drag and drop, keyboard (Alt+↑/↓) or buttons.
- **Editing**:
  - schema-driven forms with inline validation;
  - rich-text editor with an HTML source view and insertion of exploration answers;
  - media upload (embedded as data URIs and extracted to `assets/` on export) or picking from project assets;
  - visual editors to draw hotspot regions, place diagram markers and mark simulation targets.
- **Preview**: live, synchronised both ways with the editor, in desktop, tablet and mobile frames, with a reset button. Full-course preview and the LMS harness open in a new tab.
- **Course settings**: language and direction, SCORM version, pass mark, completion rule, navigation gating, transition, progress/menu/score visibility, shuffle seed.
- **Design**: 6 colours, fonts, corner radius and visual style.
- **Productivity**: undo/redo (Ctrl+Z / Ctrl+Y), autosave to IndexedDB, and reusable templates.
- **Files**: JSON import/export, and SCORM 1.2 / 2004 export that is blocked while validation errors exist.

### Learner experience

- **Layout**: app-style chrome with a top bar (progress and score), a contents drawer with done/locked states, and bottom navigation. Screens are fluid layouts rather than scaled slides.
- **Motion**: animated entrances, feedback states and confetti on success, all respecting `prefers-reduced-motion`.
- **Direction**: LTR and RTL from one stylesheet, using logical properties and mirrored charts and navigation, with Arabic UI strings.
- **Accessibility**:
  - ARIA roles (radiogroup, tablist, region, live feedback) and a visible focus style;
  - roving arrow-key focus in option groups;
  - keyboard alternatives for drag interactions (tap-to-place, move buttons, Alt+arrows);
  - alt text and captions supported, with validation warnings when they're missing.
- **Responsive**: works on desktop, tablet and phone; media and stage heights are capped to the viewport.

Defects found by this testing and fixed:
- **reveal.js and preview**:
  - a reveal.js resize-event recursion;
  - the reveal RTL setting persisting between preview reloads.
- **Learner state and progress**:
  - the resume location being overwritten before the prompt was answered;
  - worked examples marking themselves complete before being viewed;
  - game timers not resuming after the learner left and came back.
- **Keyboard and navigation**:
  - Space/arrow keys on focused controls also changing the slide;
  - gate reverts jumping back to the earliest blocked screen instead of staying put.
- **Interaction and editing**:
  - the drop-zone tap target being covered;
  - the background editor dropping the colour when "dark" was toggled.
- **Packaging**: uploaded assets embedded in HTML being reported as missing files.
- **Layout and sample content**:
  - the hotspot sample coordinates;
  - chart tick scaling and mobile legibility;
  - oversized media at small viewport heights;
  - header overflow in the studio.

## Limitations and notes

- **Real LMS certification**: tracking was verified against the strict mock LMS in `lms-test.html`, which validates vocabularies, formats, lengths and call order. It was not imported into a production LMS or SCORM Cloud from here, so please run a pilot in your LMS. The 2004 manifest references the standard XSD names but does not bundle the XSD files; most LMSs accept this.
- **Single SCO**: a course exports as one SCO with one score. Multi-SCO packages (one item per module) are not generated automatically, though separate courses can be listed in a manifest by hand as before.
- **Polls**: benchmark bars use author-provided reference data. Live aggregation across learners would need a server and is outside SCORM.
- **Video tracking**: watch tracking works for MP4/WebM files. YouTube and Vimeo embeds play, but their completion cannot be tracked (the studio warns about this).
- **The `game` type**: implements three concrete templates (quiz show, memory match, word scramble) with lives, timers, hints, streaks and pass ratio. The reference's free-form rules engine (`when/if/then`) is not implemented; branching games with scoring are covered by `decision_scenario`.
- **Escape-room answers** are stored in the course JSON in the browser. Like any client-side SCORM content, a technical learner could read them.
- **UI languages**: interface strings exist in English and Arabic. Other languages fall back to English labels; authored content can be in any language.
- **Uploads**: large uploads are embedded in the course JSON until export. Very large media should live in `media/` and be referenced by path. The studio warns above 2 MB and refuses above 12 MB.
- **Packaging needs http://**: SCORM export in the studio requires `node tools/serve.js`, because browsers block reading project files from `file://`. The CLI works anywhere.
